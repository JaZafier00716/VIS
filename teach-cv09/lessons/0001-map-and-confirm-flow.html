2 · One click, traced

This is the slide’s Scénář B (“potvrzení objednávky”). In the console it is menu item 11; in the demo it is Cv09Demonstrations, block “Scénář B”.

  1. UIMain, case "11": execute(new ConfirmOrderCommand(context.orderService(), id)). The UI builds an object; it doesn’t call confirmOrder itself.
  2. CommandOrderCommandExecutor.execute(command) calls command.execute() without knowing which command it is, and catches a rejection.
  3. CommandConfirmOrderCommand.execute() → orderService.confirmOrder(orderId). The service is the receiver.
  4. BLOrderService.changeStatus(id, Order::confirm): load the order → order.confirm() → orders.update → commit().
  5. DomainOrder.changeStatus(expected, target) checks OrderStatus.canChangeTo. Invalid → IllegalStateException, nothing changes. Valid → the change is only recorded as pending.
  6. ObserverAfter the commit succeeds, the service attaches its observers, calls order.publishStatusChanges(), then detaches them. ProductionObserver prints “Objednávka … potvrzena – připravit výrobu”.
  7. CommandBack in the executor: a CommandLogEntry(time, operation, orderId, success, message) goes into the log (slide step 5).
  8. FactoryThe demo then calls orderDocumentService().createDocument(id, new ConfirmationCreator()) → produce() → the factory method createDocument() → new OrderConfirmation(order).

Here is step 4–6 in the real code (src/business/service/OrderService.java):

private void changeStatus(String orderId, Consumer<Order> transition) {
    Order order = findOrder(orderId);
    transition.accept(order);           // Order::confirm – throws if the transition is invalid
    orders.update(order);
    try {
        commit();
    } catch (RuntimeException e) {
        order.discardStatusChanges();   // not saved → nobody is told
        throw e;
    }
    observers.forEach(order::registerObserver);
    try {
        order.publishStatusChanges();   // notify only AFTER a successful save
    } finally {
        observers.forEach(order::unregisterObserver);
    }
}

Why “pending, then publish”? The slide’s Observer page says: “Neplatná nebo neúspěšná změna stavu nesmí vyvolat oznámení. Pokud změnu také ukládáte, návazné oznámení proveďte až po úspěšném uložení.” If production were told first and the save then failed, it would start building furniture for an order that is still “Nová” in the database.
