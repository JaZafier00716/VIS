Singleton · Úkol 1

business.service.numbering.OrderNumberGenerator: private static final INSTANCE, private ctor, getInstance(), synchronized getNextNumber() from 1001. Called in OrderService.newOrder → order.assignNumber(...) (so also PlaceOrderService). Order.number ≠ Order.id.

Why: two generators could hand out the same number. Limit (slide): one instance per run, not persistence — the number is in memory only, reloaded orders have number == null, so messages show the ID.

Strategy · Úkol 2

business.pricing.IPricingStrategy { getName(); Money calculate(Order) } ← StandardPricing (sum of OrderItem::totalPrice), CompanyPricing (standard × 0.90). Context: OrderPricingService.calculatePrice(orderId, strategy). UI: menu 17 (s/f). CV08 calculate() uses StandardPricing for the items total.

Why: new pricing = new class, no if in the service. The 10 % is never stacked with the CV08 DiscountPolicy. Test: 2 × 1 000 Kč → 2 000 / 1 800.

Factory Method · Úkol 3

Product: abstract OrderDocument (getTitle(), getContent()) ← OrderConfirmation, DeliveryNote, Invoice. Creator: abstract DocumentCreator with factory method protected abstract createDocument(Order) and final shared logic produce(), render() ← ConfirmationCreator, DeliveryNoteCreator, InvoiceCreator. Service: OrderDocumentService.createDocument(orderId, creator). UI: menu 18 (p/d/f).

Why: the subclass decides the concrete type, not a switch on a string (slide “Důležité”). Invoice = the extension, added without touching DocumentCreator.

Observer · Úkol 4

Subject: Order — transient observers, registerObserver, unregisterObserver, pending StatusChanges, publishStatusChanges(), discardStatusChanges(). Observers: IOrderObserver.statusChanged(order, old, new) ← ProductionObserver (→ Potvrzená), ExpeditionObserver (→ Připravena k expedici); output via Consumer<String>. Registered in Main constructor on context.orderService().

Why pending + publish: invalid or unsaved change must not notify; notify only after a successful commit (slide). Observers are attached only during publish, so an unregistered one is never reached via a cached order.

Command · Úkol 5

IOrderCommand { getName(); getOrderId(); execute(); } ← ConfirmOrderCommand, StartProductionCommand, PrepareExpeditionCommand (each holds OrderService = receiver + orderId; Lombok @RequiredArgsConstructor). Invoker: OrderCommandExecutor.execute() → CommandLogEntry(time, operation, orderId, success, message), getLog(). UI: menu 11, 15, 16, history 19.

Why: one uniform way to run and log operations; new action = new class. No Undo (slide says not required). Invalid transition → logged as “odmítnuto”, not thrown.

Status life cycle

OrderStatus: CEKA_NA_POTVRZENI “Nová” → POTVRZENA → VE_VYROBE → PRIPRAVENA_K_EXPEDICI → EXPEDOVANA → UZAVRENA. Rule: canChangeTo(target) == (target == next()). Transitions in Order: confirm, startProduction, prepareForExpedition, ship, close.
