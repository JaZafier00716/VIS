### TDS-4 Redundancy menus.project_id / menus.name vs. their MENU node is not enforced (3NF claim and integrity)
- Severity: medium
- Evidence: 01_schema.sql `menus` (project_id, node_id, name) and `project_nodes` (project_id, node_type, name). Nothing stops `menus.node_id` pointing to a FOLDER/DOCUMENT node, to a node of another project, or `menus.name <> node.name` (verified 0 mismatches only in the seed). Not covered by 03 section 5 checks. Notes claim 3NF ("no non-key column depends on another non-key column"): `menus.project_id` and `menus.name` are functionally determined by `node_id` (menus.node_id is UNIQUE, i.e. a candidate key).
- Why: a transitive dependency/duplicate fact in the database that the notes claim does not exist; also the UI can rename a node without renaming the menu. Defence risk: teacher checking 3NF.
- Fix (KISS): either (1) document it as a deliberate denormalisation in "Normal forms" (project_id kept for the non-transferable rule and fast lookups) and add a 4th integrity check `menus whose node is not a MENU node of the same project` to 03; or (2) drop `menus.name` and use the node name (view/join). Option 1 needs no schema change. A composite FK `(node_id, project_id)` -> `project_nodes(node_id, project_id)` (needs a unique constraint on that pair) would enforce the project part in the DB.
- Confidence: confirmed
