# CV07 – Mapping the Customer hierarchy to tables

Task 2 of CV07 (cv07 p.16): design all three strategies for storing the hierarchy
`Customer` (abstract) → `PersonCustomer`, `CompanyCustomer` (cv07 p.3). The object model in
`business.domainmodel` is the same for every strategy (cv07 p.4). Only the schema and the mapping code in the
data access layer change.

| Class | Attributes | Where defined |
|---|---|---|
| `Customer` (abstract) | `customerId`, `email`, `phone`, `billingAddress` (`BillingAddress`: street, city, zipCode, country) | common |
| `PersonCustomer` | `firstName`, `lastName`, `birthDate` | person only |
| `CompanyCustomer` | `companyName`, `ico`, `dic`, `contactPerson` | company only |

The **billing address** is an Embedded Value (cv06 p.13): it has no ID and is stored as four columns,
`billing_street`, `billing_city`, `billing_zip_code` and `billing_country`, in whichever table holds the common
attributes. It is optional: no address means four `NULL` columns, and a `CHECK` constraint allows only all four
or none (a partly filled address is also rejected when a customer is loaded). The **delivery addresses** (`Address`, loaded lazily) keep their own `addresses` table.

The rest of the schema (`materials`, `finishes`, `material_finishes`, `order_items`) does not depend on the
strategy and is not repeated here. Only `orders` and `addresses` reference the customer, so they are shown for
each strategy.

Where the billing address goes in each strategy:

| Strategy | Table(s) with `billing_street`, `billing_city`, `billing_zip_code`, `billing_country` | All-or-none CHECK |
|---|---|---|
| STI | `customers_sti` (the single table) | `ck_customers_sti_billing` |
| CTI | `customers` (the common table only, not the subtype tables) | `ck_customers_billing` |
| Concrete | both `person_customers` and `company_customers` (repeated) | `ck_person_customers_billing`, `ck_company_customers_billing` |

## 1. Single Table Inheritance (cv07 p.5–6)

One table, `customers_sti`, holds both subtypes. `customer_type` is the discriminator (`P` = person,
`C` = company), and the columns of the other subtype stay `NULL`.

```sql
CREATE TABLE customers_sti (
    customer_id      VARCHAR(64)  PRIMARY KEY,
    customer_type    CHAR(1)      NOT NULL,
    -- common attributes (Customer)
    email            VARCHAR(200) NOT NULL,
    phone            VARCHAR(30),
    billing_street   VARCHAR(200),
    billing_city     VARCHAR(100),
    billing_zip_code VARCHAR(20),
    billing_country  VARCHAR(100),
    -- PersonCustomer
    first_name       VARCHAR(100),
    last_name        VARCHAR(100),
    birth_date       DATE,
    -- CompanyCustomer
    company_name     VARCHAR(200),
    ico              CHAR(8),
    dic              VARCHAR(12),
    contact_person   VARCHAR(200),
    -- optional billing address: all four columns or none
    CONSTRAINT ck_customers_sti_billing CHECK (
        (billing_street IS NULL AND billing_city IS NULL AND billing_zip_code IS NULL AND billing_country IS NULL)
     OR (billing_street IS NOT NULL AND billing_city IS NOT NULL AND billing_zip_code IS NOT NULL
         AND billing_country IS NOT NULL)),
    -- the right columns are filled for each type, the other type's columns are NULL
    CONSTRAINT ck_customers_sti_type CHECK (
        (customer_type = 'P'
            AND first_name IS NOT NULL AND last_name IS NOT NULL AND birth_date IS NOT NULL
            AND company_name IS NULL AND ico IS NULL AND dic IS NULL AND contact_person IS NULL)
     OR (customer_type = 'C'
            AND company_name IS NOT NULL AND ico IS NOT NULL
            AND first_name IS NULL AND last_name IS NULL AND birth_date IS NULL))
);

CREATE TABLE addresses (
    address_id  VARCHAR(64) PRIMARY KEY,
    customer_id VARCHAR(64) NOT NULL,
    street      VARCHAR(200),
    city        VARCHAR(100),
    zip_code    VARCHAR(20),
    country     VARCHAR(100),
    seq         BIGINT GENERATED BY DEFAULT AS IDENTITY,
    CONSTRAINT fk_addresses_customer FOREIGN KEY (customer_id)
        REFERENCES customers_sti(customer_id) ON DELETE CASCADE
);

CREATE TABLE orders (
    order_id     VARCHAR(64) PRIMARY KEY,
    customer_id  VARCHAR(64) NOT NULL,
    material_id  VARCHAR(64) NOT NULL,
    width        DOUBLE PRECISION NOT NULL,
    height       DOUBLE PRECISION NOT NULL,
    depth        DOUBLE PRECISION NOT NULL,
    design_notes VARCHAR(1000),
    status       VARCHAR(40) NOT NULL,
    created_at   TIMESTAMP(9) WITH TIME ZONE NOT NULL,
    CONSTRAINT fk_orders_customer FOREIGN KEY (customer_id) REFERENCES customers_sti(customer_id),
    CONSTRAINT fk_orders_material FOREIGN KEY (material_id) REFERENCES materials(material_id)
);
```

- **Tables:** 1 (`customers_sti`).
- **PK:** `customer_id`.
- **FKs:** `orders.customer_id` and `addresses.customer_id` → `customers_sti.customer_id`, which is an ordinary FK
  (cv07 p.11).
- **Common attributes:** the columns `email` through `billing_country`, together with the billing address.
- **Specific attributes:** in the same row. The `CHECK` constraint enforces which ones must be filled for each
  type (cv07 p.5: "složitější kontrola povinných atributů").
- **Delete:** deleting a customer cascades to `addresses`, and the FK from `orders` blocks deleting a customer who
  has orders.
- **Load:** read one row, then build a `PersonCustomer` or `CompanyCustomer` according to `customer_type`
  (cv07 p.6 step 5).

## 2. Class Table Inheritance (cv07 p.7–8)

The common table `customers` has one row per customer. Each subtype has its own table, and its `customer_id`
is both the **PK and an FK** to `customers`.

```sql
CREATE TABLE customers (
    customer_id      VARCHAR(64)  PRIMARY KEY,
    customer_type    CHAR(1)      NOT NULL,
    email            VARCHAR(200) NOT NULL,
    phone            VARCHAR(30),
    billing_street   VARCHAR(200),
    billing_city     VARCHAR(100),
    billing_zip_code VARCHAR(20),
    billing_country  VARCHAR(100),
    CONSTRAINT ck_customers_type CHECK (customer_type IN ('P', 'C')),
    CONSTRAINT ck_customers_billing CHECK (
        (billing_street IS NULL AND billing_city IS NULL AND billing_zip_code IS NULL AND billing_country IS NULL)
     OR (billing_street IS NOT NULL AND billing_city IS NOT NULL AND billing_zip_code IS NOT NULL
         AND billing_country IS NOT NULL))
);

CREATE TABLE person_customers (
    customer_id VARCHAR(64)  PRIMARY KEY,
    first_name  VARCHAR(100) NOT NULL,
    last_name   VARCHAR(100) NOT NULL,
    birth_date  DATE         NOT NULL,
    CONSTRAINT fk_person_customers_customer FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id) ON DELETE CASCADE
);

CREATE TABLE company_customers (
    customer_id    VARCHAR(64)  PRIMARY KEY,
    company_name   VARCHAR(200) NOT NULL,
    ico            CHAR(8)      NOT NULL,
    dic            VARCHAR(12),
    contact_person VARCHAR(200),
    CONSTRAINT fk_company_customers_customer FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id) ON DELETE CASCADE
);

-- addresses and orders as in STI, with REFERENCES customers(customer_id)
```

- **Tables:** 3 (`customers`, `person_customers`, `company_customers`).
- **PKs:** `customers.customer_id`. The `customer_id` of each subtype table is both a PK and an FK.
- **FKs:** subtype table → `customers` (`ON DELETE CASCADE`, so deleting the common row also deletes the subtype
  row). `orders.customer_id` and `addresses.customer_id` → `customers.customer_id`, so the order references
  the common table.
- **Common attributes:** in `customers`, together with the billing address. `customer_type` (cv07 p.7 lists it in
  `customers`) tells the DAL which subtype table to read without probing both.
- **Specific attributes:** one row in `person_customers` or one row in `company_customers`, under the same ID.
- **Insert:** `customers` first, then the subtype table, in **one transaction** (cv07 p.8 step 4). In this
  project that transaction is the Unit of Work's single JDBC connection.
- **Load:** a `JOIN` on `customer_id`, or `customers` followed by the subtype table chosen by `customer_type`.
  Then build the complete instance (cv07 p.8 step 5).
- **Update and delete:** both rows (cv07 p.8 step 6).
- **"Exactly one subtype row":** the FK guarantees only that a subtype row has a parent. It does not prevent a
  customer with no subtype row, or with rows in both tables (cv07 p.8 "Důležité"). The DAL enforces it: it
  writes both rows in one transaction, checks `customer_type` against the table it writes to, and treats a
  missing or second subtype row on load as an integrity error.

## 3. Concrete Table Inheritance (cv07 p.9–11), design only

There is one table per concrete class, and each table repeats the common columns. No common `customers` table
exists.

```sql
CREATE TABLE person_customers (
    customer_id      VARCHAR(64)  PRIMARY KEY,
    email            VARCHAR(200) NOT NULL,
    phone            VARCHAR(30),
    billing_street   VARCHAR(200),
    billing_city     VARCHAR(100),
    billing_zip_code VARCHAR(20),
    billing_country  VARCHAR(100),
    first_name       VARCHAR(100) NOT NULL,
    last_name        VARCHAR(100) NOT NULL,
    birth_date       DATE         NOT NULL,
    CONSTRAINT ck_person_customers_billing CHECK (
        (billing_street IS NULL AND billing_city IS NULL AND billing_zip_code IS NULL AND billing_country IS NULL)
     OR (billing_street IS NOT NULL AND billing_city IS NOT NULL AND billing_zip_code IS NOT NULL
         AND billing_country IS NOT NULL))
);

CREATE TABLE company_customers (
    customer_id      VARCHAR(64)  PRIMARY KEY,
    email            VARCHAR(200) NOT NULL,
    phone            VARCHAR(30),
    billing_street   VARCHAR(200),
    billing_city     VARCHAR(100),
    billing_zip_code VARCHAR(20),
    billing_country  VARCHAR(100),
    company_name     VARCHAR(200) NOT NULL,
    ico              CHAR(8)      NOT NULL,
    dic              VARCHAR(12),
    contact_person   VARCHAR(200),
    CONSTRAINT ck_company_customers_billing CHECK (
        (billing_street IS NULL AND billing_city IS NULL AND billing_zip_code IS NULL AND billing_country IS NULL)
     OR (billing_street IS NOT NULL AND billing_city IS NOT NULL AND billing_zip_code IS NOT NULL
         AND billing_country IS NOT NULL))
);

-- No common table, so no ordinary FK to "a customer": the reference is customer_id + customer_type (cv07 p.11).
CREATE TABLE addresses (
    address_id    VARCHAR(64) PRIMARY KEY,
    customer_id   VARCHAR(64) NOT NULL,
    customer_type CHAR(1)     NOT NULL,
    street        VARCHAR(200),
    city          VARCHAR(100),
    zip_code      VARCHAR(20),
    country       VARCHAR(100),
    seq           BIGINT GENERATED BY DEFAULT AS IDENTITY,
    CONSTRAINT ck_addresses_customer_type CHECK (customer_type IN ('P', 'C'))
);

CREATE TABLE orders (
    order_id      VARCHAR(64) PRIMARY KEY,
    customer_id   VARCHAR(64) NOT NULL,
    customer_type CHAR(1)     NOT NULL,
    material_id   VARCHAR(64) NOT NULL,
    width         DOUBLE PRECISION NOT NULL,
    height        DOUBLE PRECISION NOT NULL,
    depth         DOUBLE PRECISION NOT NULL,
    design_notes  VARCHAR(1000),
    status        VARCHAR(40) NOT NULL,
    created_at    TIMESTAMP(9) WITH TIME ZONE NOT NULL,
    CONSTRAINT ck_orders_customer_type CHECK (customer_type IN ('P', 'C')),
    CONSTRAINT fk_orders_material FOREIGN KEY (material_id) REFERENCES materials(material_id)
);

-- all customers regardless of type (cv07 p.10 step 5)
SELECT customer_id, 'P' AS customer_type, email, phone FROM person_customers
UNION ALL
SELECT customer_id, 'C' AS customer_type, email, phone FROM company_customers;
```

- **Tables:** 2 (`person_customers`, `company_customers`).
- **PK:** `customer_id` in each table. The application-generated UUIDs (`IdGenerator`) keep IDs unique across
  both tables. The database cannot enforce that across two tables.
- **FKs:** none from `orders` or `addresses` to a customer, because one ordinary FK cannot point to two tables
  (cv07 p.10, p.11). Instead, `orders` and `addresses` store `customer_id` together with `customer_type`, and the
  **DAL checks the reference**. On insert it looks up `customer_id` in the table chosen by `customer_type`. On
  delete it refuses to delete a customer with orders and deletes the customer's addresses itself, which replaces
  `ON DELETE CASCADE`.
- **Common attributes:** repeated in both tables, together with the billing address.
- **Specific attributes:** in the table of their own type.
- **Load:** by type, from one table. "All customers" needs a `UNION ALL`.
- **Why it is not implemented:** you asked for a design only. It is also the strategy that would weaken the
  existing Foreign Key Mapping (cv06): `fk_orders_customer` and `fk_addresses_customer ON DELETE CASCADE` would
  have to be replaced by checks in code.

## 4. Comparison for this project (cv07 p.12)

| Property | STI | CTI | Concrete Table Inheritance |
|---|---|---|---|
| Tables for the hierarchy | 1 (`customers_sti`) | 3 (`customers`, `person_customers`, `company_customers`) | 2 (`person_customers`, `company_customers`) |
| Common attributes (email, phone, 4 billing columns) | once, in `customers_sti` | once, in `customers` | repeated in both tables |
| Unused columns | person rows: 4 company columns NULL; company rows: 3 person columns NULL | none | none |
| Required fields per subtype | only through the `CHECK` constraint | `NOT NULL` in the subtype table | `NOT NULL` in each table |
| Load one customer of a known type | one row, one table | `JOIN customers` + subtype table (2 tables) | one table |
| Load all customers | one `SELECT` | `customers` + 2 subtype tables (`LEFT JOIN` or 3 reads) | `UNION ALL` of 2 tables |
| Insert one customer | 1 `INSERT` | 2 `INSERT`s in one transaction | 1 `INSERT` |
| FK from `orders`/`addresses` | yes, to `customers_sti` | yes, to `customers` | no; `customer_id` + `customer_type`, checked by the DAL |
| `ON DELETE CASCADE` to addresses | yes | yes (and to the subtype row) | no, done by the DAL |
| "Exactly one subtype row" | given (one row) | enforced by the DAL | given (one row) |
| Adding a third customer type | add columns, widen the CHECK | add one table | add one table, update every UNION and reference check |

### Why CTI and STI were chosen

- Both keep **one common table that `orders` and `addresses` can reference with an ordinary FK**. The CV06
  Foreign Key Mapping (`fk_orders_customer`, `fk_addresses_customer ON DELETE CASCADE`) therefore stays exactly
  as it is, and only the referenced table changes. Concrete Table Inheritance would replace both with checks in
  code (cv07 p.11).
- **STI** fits this hierarchy well: there are only two subtypes, with three and four specific columns, and it gives
  the simplest queries (cv07 p.12, "málo potomků … jednoduché dotazy"). Its weak point, the required fields per
  type, is covered by the `CHECK` constraint.
- **CTI** has no `NULL` columns and gives each subtype's required fields a real `NOT NULL`. It suits the case
  where the subtypes grow their own attributes (cv07 p.12, "potomci více vlastních atributů"). Its cost is the
  two-table insert, which the Unit of Work's single transaction already provides.
- Implementing both behind the same `CustomerRepository` shows the point of cv07 p.4: the object model stays the
  same, and only the schema and the mapping in the DAL change.

## 5. Likely examiner questions

**1. Why does CTI need one transaction, and how do you guarantee it?**
One customer is two rows: the common row in `customers` and the subtype row in `person_customers` or
`company_customers` (cv07 p.8 step 4). If the second insert failed on its own, an orphan `customers` row without a
type would remain. `CtiCustomerTables.insert` writes `customers` first and then the subtype row, and both writes
run inside `UnitOfWork.commit()`, which holds one JDBC connection with `autoCommit=false` on H2 (the file journal
on JSON). Any failure rolls both back. `InheritanceStrategyRulesTest.ctiRollsBackTheCommonRowWhenTheSubtypeInsertFails`
makes the subtype insert fail and checks that `customers` stays empty.

**2. How does STI know which class to build?**
From the discriminator `customer_type` (`P` = person, `C` = company, cv07 p.5). `StiCustomerTables.toDomain`
switches on it and hands the row's columns to `PersonCustomerMapper` or `CompanyCustomerMapper`. The CHECK
constraint `ck_customers_sti_type` (and the same rule in `JsonStiCustomerGateway`) guarantees that a `P` row has
the person columns filled and the company columns NULL, and the other way round, so the discriminator and the data
cannot disagree.

**3. Why can't Concrete Table Inheritance use a normal foreign key from `orders`?**
There is no common customer table: a person is in `person_customers` and a company in `company_customers`
(cv07 p.9–11). An FK points to exactly one table, so `orders.customer_id` cannot reference "either table". The
design stores `customer_id` + `customer_type`, and the DAL must check the reference and replace
`ON DELETE CASCADE` itself. That is also why it was not chosen: it would replace the CV06 Foreign Key Mapping
with code.

**4. Where are the Inheritance Mappers, and what does each part do?**
In the data access layer, `dataaccess.mapper.customer` (cv07 p.13). `CustomerInheritanceMapper` is the common
part: it maps ID, e-mail, phone and the billing address (Embedded Value, all four columns or none) to the common
record. `PersonCustomerMapper` and `CompanyCustomerMapper` add the specialised part and build the complete
instance. They do not know tables: `CtiCustomerTables` and `StiCustomerTables` only decide where the common and
the specific part are stored. Both strategies share the same mappers.

**5. What did you have to change in the business layer to support two strategies?**
Nothing that depends on the strategy (cv07 p.14). The business layer got the hierarchy itself (`Customer`
abstract, two subclasses with their validation) and `createPersonCustomer` / `createCompanyCustomer`, because the
user chooses the type (cv07 p.15). `CustomerRepository` is unchanged and still works with `Customer`; the
strategy is chosen in `ApplicationContext` (`--mapping=cti|sti`). One change was needed in the data access layer
that is easy to miss: the Identity Map keys by the hierarchy root, so `Customer#C-1` finds a `PersonCustomer`.
